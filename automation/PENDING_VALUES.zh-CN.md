# 保存待出数状态期望概率：设计与现状

本文记录“只保存下一次随机预览揭晓前的期望概率，运行时搜索动作”的方案及其在独立 10 格 10240 模式中的接入。这里的成功概率指**在对应定式模型内最终达到该定式出口的概率**，不是整局游戏的胜率。

## 状态与压缩原理

现有转移表的完整决策状态是 `(B, q1, q2)`：`B` 为活动棋盘（含虚拟固定段 F 的位置），`q1` 是本次要投放的数字，`q2` 是已经可见的下一数字。选择动作并投放 `q1` 后，得到新棋盘 `B'`；原 `q2` 前移为下一次的当前数字，新的预览 `q3` 此时才随机产生。

设 `V(B, q1, q2)` 为完整状态的后续成功价值。对于一个非终止动作，只保存尚未揭晓 `q3` 时的期望：

```text
W(B', q2) = Σ P(q3) · V(B', q2, q3)
```

当前模型的出数集合为 `{2, 4, 6, 8, 10, 15}`，六种 `q3` 各占 `1/6`。因此 `W` 是六个完整后继状态价值的平均。这里平均的是**动作结束后才出现的 q3**；运行时仍使用当前已知的 `q1` 和 `q2` 决策。求解 `V` 时，每个 `q3` 揭晓后都可以选择不同的后续动作。

转移表原本就把同一 `(B', q2)` 的六个后继状态组成一组。只要每组齐全，期望条目数就是完整状态数的 `1/6`。这是条目数的比例；整个文件还包含状态编码、模型参数和棋盘字典，所以文件大小不一定正好缩为 `1/6`。

## 离线构建

实现位于 [`pending_value.cpp`](pending_value.cpp)，生成入口为 `build TABLE VALUES OUTPUT`：

1. 读取转移表及与其顺序对应的完整状态值数组；检查每个 `(棋盘, q1)` 分组都包含六种预览结果。
2. 对每组六个值取平均，以去掉 `q2` 位后的状态编码作为键，并按键排序。
3. 写出 `TNPEND01` 文件：模型参数、完整状态数、待定状态数、每条 8 字节编码与 8 字节浮点期望，以及用于还原棋盘的字典。

生成期望表仍需要完整转移表和完整值函数。当前构建器通过 `solver::loadMDP` 加载转移关系，节省的是**运行时查询文件**，并不意味着离线求解内存也降为 `1/6`。源值的目标必须与“成功概率最大”一致；带步数惩罚或人为猝死的价值不能直接解释为纯成功概率。构建器主要检查文件格式、状态数和分组完整性；`TALLVAL4` 本身没有内嵌转移表指纹，因此还需用外部哈希记录其来源。

## 运行时选动作

原生查询入口为 `query PENDING_FILE`，输入格式沿用固定策略查询接口。它从当前 `(B, q1, q2)` 枚举合法免费操作（包括 Group 和 EDGE）的闭包，再考虑三种投放方向。对于每个不同的非终止结果 `(B', q2)`，查一次 `W(B', q2)`；直接成功的价值为 `1`，没有可存活动作则报告 `dead`。选中结果后，现有 `recoverPlan` 还原可执行操作序列。返回的 `score` 是**本次所选动作的模型期望**。

当两个动作期望完全相同时，当前实现保留搜索顺序中先找到的动作。这使结果可重复，但仅靠概率相等不能排除零进展循环；推广到更多定式时，需要检查并列动作和新策略的终止性。运行时还要展开免费操作闭包并查询多个候选，因此每步计算量高于直接读取固定动作。

Python 的 [`PolicyWorker`](library.py) 可通过定式条目的 `pendingValue`、`pendingValueSha256`、`pendingValueMeta`、`pendingNative` 启用此分支。它核对转移表、原策略、期望文件及旁路元数据的哈希和模型条件。动态分支现覆盖路线叶子中的 5 格 single、match、extend，3 个 6 格 single，以及 6 个 match 救援 buffer 定式。五格缓存没有覆盖当前候选时，程序回到**同一定式的原固定策略**。六格静态查询表体积很大，六格域外状态交由既有的路线入口桥接处理，避免重复加载大表。只有选择独立备选模式时才启用搜索。执行器在 [`runtime.py`](runtime.py) 中记录返回的 `score` 和五格回退标记。传统路线、策略库和入口没有被改写；动态模式仍保留原策略与转移表用于身份校验及五格回退。

## 已完成的实验

最早用目标 10 的五格定式验证了算法：62,136 个完整状态合并为 10,356 个待定状态；按期望重新导出的固定策略与原策略逐字节一致，36 种初始预览组合的查询结果一致。该目标和实验文件后来随“删除目标不超过 16 的定式”一起清理，不能再作为现存运行输入。

当前路线扩展实验入口为 [`prepare_pending_search.py`](prepare_pending_search.py)，输出到 `automation/runs/binary10240/min24/pending-search-all-policies-001/`。该目录准备了 21 个待定值文件：12 个五格 single/match/extend 路线叶子、3 个六格 single，以及 6 个 buffer 救援定式。六格版本流式读取完整转移表，不会把约 8000 万状态的完整 MDP 一次性载入内存；每张六格缓存约 253 MiB。不同出口、上限与格数仍使用各自的缓存。

先前仅覆盖 3 个五格 single 定式的 100 局配对模拟中，固定救援版完成 `49/100` 局、搜索版完成 `51/100` 局；原 JavaScript 游戏引擎核对了 100 局、`722,539` 个动作，RNG 一致且未强制出数。扩展到 21 个定义后，相同种子对照为传统版 `49/100`、搜索版 `53/100`，配对结果有 `22` 局由败转胜、`18` 局由胜转败；搜索版平均成功局投放 `6,449` 次，平均失败局投放 `1,807` 次。75 次 buffer 救援均已完成；原引擎复核了 `635,477` 个动作，RNG 一致且未强制出数。记录在 `pending-search-all-policies-001/validation-100-retry1/summary.json`。两个结果都只是 100 局的小样本，不能据此断言长期胜率提升；平均所选局部 `W` 值 `0.9941` 也不是整局胜率。

## 接入完整十格 10240 路线（独立模式）

动态搜索已有一份完整的十格 10240 路线快照；传统路线不需要改写，也不读取动态模式的目录。用下面的命令把已验证快照注册成独立的备选模式：

```powershell
python -m automation.pending_search_mode prepare
```

完整扩展版注册时会生成独立目录，含自己的 `route.json`、`catalog.json`、buffer 映射与 `mode.json`。准备脚本会验证目标为 10 格 10240、路线结构与传统路线相同、动态定义均在路线或救援图内，并检查传统路线文件哈希未变。缓存以经过哈希校验的路径引用，不复制到大体积回放或写入传统策略库。

可用同一批传统路线种子重新配对验证，或先跑小样本：

```powershell
python -m automation.pending_search_mode validate --seed-limit 1
python -m automation.pending_search_mode validate --seed-limit 100
```

验证产物分别写入备选模式目录的 `validation-1/` 或 `validation-100/`。该命令只运行 10 格仿真与原引擎回放，不启动浏览器游戏。完整模式清单记录了传统文件哈希和动态验证结果，便于以后明确选择其中一种，不会把实验策略静默并入传统实现。

## 使用边界

- `W` 与生成它的转移规则、成功条件、数字分布和优化目标绑定；修改任一条件都要重新求值并生成文件。当前模型假设六种新预览等概率，尚未完整模拟网页游戏的解锁出数机制。
- `W` 覆盖全转移表的待定状态，而固定策略验证图通常只覆盖该策略实际可达的状态。运行时改选动作可能走出原策略的可达图，所以不能仅压缩固定策略图的概率向量。
- 纯成功概率最大化可能选择更长的路线；若主要目标是包含重试在内的平均投放次数，需要相应的成本价值，而不是只比较 `W`。
- 五格搜索缓存没有覆盖的候选会尝试原定式固定策略；六格域外状态继续按现有入口桥接规则处理。若固定策略也拒绝入口，则按既有路线失败分类处理。模型概率、局部搜索次数和整局成功率应分别解读。
