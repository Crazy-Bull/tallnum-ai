# Match 定式的 buffer 救援

## 行为

`bufferRescuePolicies` 为每种 match 目标配置一个同十进制头、不同数值的已认证 buffer。match 定式遇到“策略判死”或“下一动作会吞掉受保护前缀”时，执行器在同一规格内找可用的 buffer 定式；buffer 完成后用 EDGE 消去 match 锚块，把路线阶段回退到锚块之前，再按真实盘面和当前预览重新执行后续定式。原队列、投放、RNG 和已发生的操作都保留，不伪造数字或清盘。

回退点按路线叶节点边界匹配，而不是只回退一个叶节点。因此 `40 → 80`、`32 → 64` 这类嵌套 match 可以退回到产生当前锚块的定式之前。

## 全部 match 映射

| match 目标 | buffer 目标 |
| --- | --- |
| 32 | 30 |
| 40 | 48 |
| 48 | 40 |
| 60 | 64 |
| 64 | 60 |
| 80 | 84 |

六种 buffer 都是五格、目标组合不超过四格、干净胜利条件、最大中间数字至少 48，并通过 PETSc 策略改进与两轮固定出口概率复核。映射和每个策略身份保存在运行目录的 `mapping.json`、`catalog.json` 与 `configuration.json` 中。

## 配对测试

`buffer-rescue-all-007` 使用原路线、同一批 100 个种子及原始随机队列。71 局进入救援，71 次完成 buffer 和 EDGE 清理，没有救援不可用。最终 49/100 局合成目标；相对于 `entry-bridge-004`，25 局由失败转成功，2 局由成功转失败。失败仍以固定策略问题为主：38 局策略判死、11 局动作会吞掉受保护前缀；另有 1 局入口不在定式域、1 局出口契约不匹配。模型单定式成功率不能当作整局胜率。

原 JavaScript 引擎逐步重放全部 100 局、706,810 个动作，种子 RNG 对齐，未强制出数。完整逐局记录和回放在 `automation/runs/binary10240/min24/buffer-rescue-all-007/`。

## 实时概率搜索实验

`pending_value.cpp` 把转移表的完整值函数压缩成“盘面与待出数状态 → 完成概率”，运行时枚举免费动作与三个可用投放方向，选择所达待投放状态概率最高的动作。值函数中对刚隐藏的下一个预览取平均；当前两枚可见预览仍参与具体状态编码。当前接入限定在五格 single 定式；match 仍用带 EDGE 保护的固定策略，并由上面的 buffer 救援兜底。此分支只作为实验控制器，不自动替换已验证路线；概率是定式内模型值，不代表整局胜率。

冒烟测试使用同一批 10 个种子：动态版 7/10，固定救援版也是 7/10，逐局成功与投放数相同；其中 7 局的实际操作轨迹发生变化。动态版做出 4,833 次局部概率搜索决策，原 JavaScript 引擎复核 10 局、88,939 个动作，RNG 对齐且无强制出数。

同一条路线、同一批 100 个种子的完整配对测试已完成。固定救援版为 49/100；动态搜索版为 51/100，配对结果是 2 局由失败变成功、0 局反向。动态版完成 72 次 buffer 救援，全部成功；完成 36,215 次五格 single 的局部搜索，所选状态模型概率均值为 0.999469。该均值仅表示每次局部决策的定式完成概率，不能解读为整局成功率。整局成功率在这批种子上只提升 2 个百分点，仍需更多配对样本判断提升是否稳定。失败原因由固定救援版的 38 次策略判死降至 36 次；其余主要问题没有消失：11 次受保护前缀冲突、1 次入口超出定式域、1 次出口契约不匹配。

动态运行日志通过原 JavaScript 引擎核验：100 局、722,539 个动作，种子 RNG 对齐、没有强制出数。完整逐局记录位于 `automation/runs/binary10240/min24/pending-search-single-001/validation-100/`，构建出的概率表和实验目录位于 `pending-search-single-001/`。该控制器仍只接管五格 single；match 继续使用带 EDGE 保护的固定策略和 buffer 救援。
